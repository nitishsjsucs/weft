### Regressions: 5 tasks, 4 of them an eval bug

**G5 grades with less evidence than the harness guard (eval bug, 4 dev tasks: BN-02, CP-01, OC-01, TO-01).** FG2 made
the loop's grounding guard accept the person's own request and the run clock as evidence (`check(text, results,
{ request, now, echoes })`, `packages/agent/src/loop.ts`). G5 still calls `check(text, toolResults)` with two arguments
(`evals/suite/graders/index.ts`), so it flags exactly what the guard now accepts: the request's "Oct 1 to 15", "Oct 27"
and "$1,500.00" (CP-01, OC-01), the clock's "October 2026" (BN-02) and the bounds of "next week", November 2 to
November 8 (TO-01). In all four traces the harness `grounding.check` span says `grounded=true` with no offending
figure, and every run had 0 repairs and no fallback. An offline re-check of each flagged figure with the request and
the frozen world clock grounds every one of them (`round1-g5-recheck` in the summary JSON). Three of them (CP-01, OC-01,
TO-01) passed in the baseline only after a grounding repair that dropped those figures; BN-02's baseline answer named
no date. Now the guard accepts the first answer, and G5 refuses it. With G5 using the guard's evidence, dev
would read 53 of 55 (96.4%). The fix is in the grader: pass the task request and the world clock (and the run's
echoed arguments) to `check` as the loop does. Category: eval bug, from FG2 and FG5 landing separately.

**CQ-02 "Why did payroll go up in Q3?" (tightened task, tool selection).** FG5 tightened the task to require a driver
from the data (a hire, a raise or headcount). The baseline passed with four `reports.query` calls, one of them
headcount ("Headcount was flat at 45"). Round 1 ran `reports.query` twice and `memory.search` once, never queried
headcount or hires, and answered that the report shows no Q3 increase. A single k = 1 trial, so part of this may be
variance; the task's own reference notes that the seed's Q3 holds only September paid runs, so the "driver" the
tightened check wants is a headcount line, not a real cause in the data.

### Still failing: MM-03, with a new cause

The baseline failed because the notice precheck skipped the run (0 model steps). Now the agent runs, but it follows
the generic missing-filing handling (prepares the NYS-45, proposes `tax.file_return` and `notices.send_response`) and
never escalates. The trace's `memory.recall` span shows why: the recall did hit
`knowledge/procedures/notice-escalation.md`, but the snippet it put in context is only the heading line
("id proc-notice-escalation. # Notice escalation"), so the procedure's rule (escalate with `notices.escalate`, never
claim the filing) never reached the model, and the run made no `memory.read` or `memory.search` to open it. Layer:
context and memory (a procedure hit should bring its body, or the routine recipe should read a procedure it recalls).
